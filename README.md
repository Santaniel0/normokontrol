# normokontrol

[![CI](https://github.com/Santaniel0/normokontrol/actions/workflows/ci.yml/badge.svg)](https://github.com/Santaniel0/normokontrol/actions/workflows/ci.yml)

Проверка оформления курсовых, отчётов по практике и ВКР в формате .docx по
ГОСТ 7.32-2017 или по методичке конкретного вуза. Программа работает
локально, без интернета, и поставляется одним исполняемым файлом.

## Зачем

Почти в каждом российском вузе работа перед защитой проходит нормоконтроль:
поля, шрифт, интервалы, отступы, заголовки, подписи рисунков, список
источников. Студент узнаёт о проблемах, когда нормоконтролёр возвращает работу
с замечанием вроде «разный межстрочный интервал», и дальше сам ищет, где
именно. Нормоконтролёр проверяет десятки работ вручную, абзац за абзацем.

Большинство этих ошибок механические. В исследовании КФУ
([Шахова, «Информатика и образование», 2024, № 2](https://info.infojournal.ru/jour/article/download/1084/698))
вручную разобрали 320 комплектов отчётов по практике: правильно оформлены
около 30 %, а 94 % всех найденных ошибок относятся к оформлению. Чаще всего
встречаются разный межстрочный интервал, пустые строки между абзацами, разное
выравнивание, пропущенные абзацные отступы, разные шрифты, рисунки без подписей
и без ссылок в тексте. Всё это можно найти по самому файлу .docx, и правила
этой программы выбраны по этому списку.

Типичный сценарий. Студент набирает текст в Word, часть копирует с сайтов,
отступы ставит пробелами, а интервал меняет у отдельных абзацев. Word показывает
шрифт выделенного абзаца, но не говорит, что Calibri пришёл из темы документа
через стиль «Обычный» и что исправлять нужно стиль, а не сорок абзацев.
normokontrol вычисляет итоговое оформление каждого абзаца так же, как Word,
говорит, откуда взялось значение, и сохраняет копию документа с примечаниями
Word прямо на проблемных абзацах.

## Установка

Готовый файл для Windows (`normokontrol_<версия>_windows_amd64.exe`) и сборки для Linux и macOS лежат на странице [Releases](https://github.com/Santaniel0/normokontrol/releases/latest). Go для них не нужен: файл работы можно сразу перетащить на .exe. Собрать самому через Go:

Нужен Go 1.27 или новее.

```
go install github.com/Santaniel0/normokontrol/cmd/normokontrol@latest
```

Сборка под Windows с любой системы:

```
GOOS=windows GOARCH=amd64 go build -o normokontrol.exe ./cmd/normokontrol
```

Получается один файл без зависимостей. Его можно отдать студенту: достаточно
перетащить .docx на значок программы в Проводнике. Программа проверит файл,
сохранит рядом копию с примечаниями и не закроет окно, пока не нажать Enter.

показывает копия с примечаниями: замечание висит на нужном абзаце, как
от живого нормоконтролёра. Если одна и та же ошибка повторяется много раз,
примечания ставятся на первые 20 мест.

Нормоконтролёр может проверить папку группы сразу. Файлы проверяются
параллельно, а строки выводятся в порядке файлов:

```
$ normokontrol batch --profile kafedra.toml --out отчёты --annotate ИС-41
```

## Профили

Встроенный профиль `gost-7.32-2017` можно посмотреть командой
`normokontrol profile`. Каждое значение в нём сверено с текстом стандарта, а в
комментарии указан пункт: поля 30/15/20/20 мм, полуторный интервал, абзацный
отступ 1,25 см (6.1.1), заголовки структурных элементов (6.2.1), подписи
рисунков и таблиц (6.5.7, 6.6.3). Где ГОСТ оставляет решение организации,
значение не задано. Выравнивание основного текста стандарт не устанавливает,
поэтому по умолчанию проверяется только его единообразие. Times New Roman в
ГОСТ только рекомендован, поэтому другой шрифт даёт предупреждение, а не
ошибку.

Профиль кафедры наследует встроенный и меняет только то, что отличается
(полный пример — `examples/kafedra.toml`):

```toml
base = "gost-7.32-2017"
name = "Кафедра информационных систем, ВКР 2026"

[body]
font_required = true
size_pt = 14
align = "justify"

[rules]
disable = ["refs.order"]
```

Опечатка в имени параметра не пропускается молча: программа сообщит
«неизвестный параметр page.margin_lft_mm». Если положить `normokontrol.toml`
рядом с программой, он подхватится без флага `--profile`. Так кафедра может
раздать студентам программу вместе со своими требованиями.

Список правил выводит `normokontrol rules`:

```
page.margins     формат страницы и поля в каждом разделе документа (6.1.1)
structure        обязательные структурные элементы и их порядок (раздел 4, 6.2.1)
heading.format   заголовки: без точки в конце, структурные — прописными и по центру (6.2.1, 6.2.3)
body.font        шрифт и кегль основного текста, вставки другим шрифтом (6.1.1)
body.spacing     межстрочный интервал (6.1.1)
body.align       выравнивание основного текста (ГОСТ не задаёт, проверяется единообразие)
body.indent      абзацный отступ, в том числе сделанный пробелами или табуляцией (6.1.1)
body.empty       пустые абзацы вместо интервалов и разрывов страниц
captions         подписи рисунков и таблиц, нумерация, ссылки в тексте (6.5, 6.6)
refs.citations   ссылки [N] и список источников (6.9.1)
refs.order       порядок источников по первым ссылкам (6.16)
text.homoglyph   латинские буквы в русских словах и наоборот
```

## Как это работает

**Чтение файла.** .docx — это zip-архив с XML внутри. Перед чтением программа
проверяет число файлов в архиве и их суммарный распакованный размер. Размеру из
заголовка zip она не доверяет и читает каждую часть с ограничением. Так
повреждённый или специально собранный файл не съест память. Файлы .doc и
документы с паролем внутри устроены иначе (OLE): они распознаются по сигнатуре,
и программа просит пересохранить файл.

**Итоговое оформление.** `document.xml` разбирается за один потоковый проход
(`encoding/xml`). Свойство абзаца или фрагмента текста может быть задано в
нескольких местах: умолчания документа, цепочка стилей абзаца через `basedOn`,
стиль знака и прямое форматирование. Пакет `internal/format` проходит этот
каскад в том же порядке, что и Word, и для каждого значения запоминает
источник. Отсюда в отчёте строки «источник: стиль «Обычный» → шрифт темы». В
каскаде есть детали, которые легко упустить. Кириллицу Word рисует шрифтом из
слота `w:hAnsi`, а латиницу — из `w:ascii`, поэтому в одном абзаце может
оказаться два разных шрифта. Полужирное начертание переключается: стиль знака
«полужирный» на полужирном заголовке снимает выделение. Русский Word называет
стили «a», «1», «a0», так что опираться на идентификатор стиля нельзя:
программа смотрит на `w:name` и на уровень структуры.

**Роли абзацев.** Каждый абзац получает роль: заголовок, основной текст,
подпись, рисунок, ячейка таблицы, элемент списка, строка содержания, источник,
формула, код или титульная часть. Заголовки распознаются по стилю и уровню
структуры. Набранные вручную «ВВЕДЕНИЕ» или полужирное «2 Проектирование
системы» тоже узнаются, но за отсутствие стиля выдаётся предупреждение.
Правила о шрифте и отступах применяются только к основному тексту: титульный
лист, таблицы, код и приложения живут по своим правилам, и иначе программа
завалила бы отчёт ложными замечаниями. Если профиль значение не задаёт, а
больше половины абзацев основного текста оформлены одинаково (например,
выровнены по ширине), отклонения от этого большинства выдаются как
предупреждения.

**Примечания Word.** Копия с примечаниями не пересобирает XML: `encoding/xml`
не сохраняет префиксы пространств имён, а Word отказывается открывать документ,
у которого `w:` заменён на что-то другое. При разборе для каждого абзаца
запоминаются байтовые смещения в исходном `document.xml`, и метки примечаний
вставляются прямо в эти места. Существующие примечания руководителя
сохраняются, новые получают следующие номера. Если частей
`comments.xml`, связи и типа содержимого нет, они добавляются. Остальные части
архива (стили, картинки) копируются как есть, в сжатом виде, байт в байт; это
проверяется тестами. Копия пишется во временный файл и переименовывается
только после успешной записи.

У самого zip-архива есть своя тонкость. Стандартный `zip.Writer` пишет
данные потоком: размеры и контрольная сумма попадают не в заголовок файла, а
в «дескриптор» после данных. Формат это допускает, но LibreOffice такой .docx
не открывает. Поэтому каждая часть сначала сжимается в памяти, а потом
записывается через `CreateRaw` с уже известными размерами (пакет
`internal/zipx`). Тест читает байты локальных заголовков и проверяет, что
дескрипторов нет.

**Пакетная проверка.** `batch` раздаёт файлы пулу горутин (по умолчанию по
числу ядер). Результаты печатаются в исходном порядке, как только готов
очередной файл. По Ctrl+C новые файлы не запускаются, а оставшиеся помечаются
как непроверенные.

## Разработка

```
go vet ./...
go test ./...
go run ./cmd/mksample                     # пересобрать testdata/*.docx
go test ./internal/check -update          # обновить эталонный отчёт testdata/vkr_bad.report.txt
```

Две проверки нужно запускать вручную (Windows PowerShell 5.1), потому что в CI
нет офисных программ:

```
powershell -ExecutionPolicy Bypass -File scripts\verify-libreoffice.ps1
powershell -ExecutionPolicy Bypass -File scripts\validate-openxml.ps1 -Sdk C:\tools\openxml
```

Первая конвертирует оба образца и копию с примечаниями в ODT через LibreOffice
и сверяет число примечаний Word с числом `office:annotation` в результате.
По умолчанию она ищет LibreOffice в `C:\Program Files\LibreOffice`, другой путь
задаётся параметром `-Soffice`. Вторая проверяет те же файлы валидатором
Open XML SDK по схемам Office 2019. В `-Sdk` нужна папка, куда распакованы два
пакета с nuget.org: `DocumentFormat.OpenXml` и `DocumentFormat.OpenXml.Framework`
версии 3.5.1.

Тесты собирают небольшие .docx прямо в коде (`internal/docxtest`) и проверяют
каждый уровень каскада стилей, распознавание ролей, каждое правило, а также что
документ без нарушений не даёт ни одного замечания. Для примечаний есть тест
полного цикла: файл перечитывается, количество примечаний и меток сходится,
старые примечания на месте, нетронутые части архива совпадают байт в байт. Для
чтения архива есть fuzz-тест. CI на GitHub Actions запускает `gofmt`,
`go vet`, `go test -race` и сборку под Linux и Windows.

## Ограничения

- В Microsoft Word копия с примечаниями не открывалась: Word на машине
  разработки не было. Проверено другое. LibreOffice 26.8.2 открывает оба
  образца и копию с примечаниями, и все 24 примечания из копии доходят до
  ODT. Валидатор Open XML SDK 3.5.1 по схемам Office 2019 не находит в этих
  трёх файлах ни одной ошибки.
- Все тестовые документы синтетические, их собирает код. На реальных работах
  из Word могут встретиться конструкции, которых в тестах нет: списки со
  своими отступами из `numbering.xml`, стили таблиц, поля, текст в надписях.
  Абзацы списков исключены из проверки отступов, а ячейки таблиц — из
  проверки шрифта, чтобы не давать ложных замечаний.
- Программа не знает, на какой странице оказался абзац. Нельзя проверить номера
  страниц в содержании, перенос подписи на следующую страницу, «висячие»
  строки.
- Поля альбомных разделов не проверяются: вузы по-разному требуют их
  считать.
- Распознавание заголовков, набранных без стиля, эвристическое. Короткий
  полужирный абзац, начинающийся с номера, будет принят за заголовок.

## Не входит в v1

- Веб-интерфейс и HTML-отчёт.
- Форматы .doc, .odt и PDF (.doc нужно пересохранить в Word как .docx).
- Автоматическое исправление оформления.
- Проверки, которым нужна вёрстка страниц: номера страниц, содержание,
  переносы.
- Нумерация страниц в колонтитулах.
- Проверка библиографического описания по ГОСТ Р 7.0.100-2018 (проверяются
  только ссылки [N] и нумерация списка).
- Антиплагиат, поиск текста от нейросетей, орфография.
- Формулы, рамки и штампы ЕСКД, шаблон титульного листа.
